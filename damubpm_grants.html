Как устроены проверки полномочий в DamuBPM

Кто может видеть список, открыть карточку, создать, изменить или удалить запись сущности. По Go-коду CheckGrantOfEntity, CheckFullGrantOfEntity, QueryGetViewQueryLimit и данным стенда contact-center на 19.10.2026.

1 801грант в entity_grants
3 457ограничений в entity_view_limits
2 159автоматических «1 = 1»
1 246ограничений с :user_id

1. Модель данных

entity_grants — роль × сущность × ограничение × действия

КолонкаСмысл
role_idкому выдано
entity_idна какую сущность
view_limit_idна какие строки; обязательно — без него грант не участвует в JOIN
is_list_viewвидеть в списках
is_detail_viewоткрывать карточку
is_insert / is_update / is_deleteсоздавать / изменять / удалять
edit_only_attrменять только атрибуты из entity_grants_edit_attr

Ключ на практике — (view_limit_id, entity_id, role_id). У одной роли на сущность может быть несколько грантов с разными ограничениями.

entity_view_limits — какие строки

КолонкаСмысл
subquerySQL-условие в WHERE, таблица сущности под алиасом main
is_auto1 — создано платформой вместе с сущностью: code = код сущности, subquery = '1 = 1'
for_filterиспользуется как фильтр списка
warning_textошибка SQL, пишет БП entity_view_limits_upsert

Плейсхолдеры: :user_id — везде; :lang — только в списках (QueryGetViewQueryLimit), в проверке записи не заменяется; :detail_id, :detail_query_id — только в валидаторе (подставляет 0).

Параметр роли is_admin = 1 (на стенде — роль admin) обходит ограничения. Параметр пользователя readonly_mode = 1 запрещает запись.

2. Проверка одной записи — CheckGrantOfEntity

  1. Белый список прав. grant ∈ is_list_view, is_detail_view, is_update, is_delete, is_insert (+ edit_only_attr при FeatureGrantEditAttr). Имя права вставляется в SQL как колонка — список закрыт от инъекций.
  2. Администратор. При skipAdmin и is_admin = 1 — доступ сразу.
  3. Только чтение. Для insert/update/delete при readonly_mode = 1 — E-BPM-00030. Readonly Mode.
  4. Сбор ограничений всех ролей пользователя, где eg.<grant> = 1. Пусто — Access Denied.
  5. Объединение через OR: (sq1 or sq2 …), :user_id → число. Права ролей складываются.
  6. Проверка строки: select 1 from <entity> main where main.id = ? and (…). Нет строки или ошибка SQL — отказ.
select evl.subquery
from entity_grants eg, entities e, entity_view_limits evl, user_roles ur
where eg.<grant> = 1 and e.code = ? and e.id = eg.entity_id
  and eg.view_limit_id = evl.id and ur.role_id = eg.role_id and ur.user_id = ?
Проверка идёт по числовому main.id. Для is_insert проверяется уже существующая строка — до вставки этой функции недостаточно. Ошибка SQL в любом ограничении ломает проверку для всех ролей пользователя.

CheckFullGrantOfEntity

То же, но учитываются только гранты с coalesce(edit_only_attr,0) = 0. Нужна для полной правки формы и удаления. CheckGrantOfEntity(…, "is_update", …) пропустит и пользователя с грантом «только отдельные атрибуты».

3. Ограничение списков — QueryGetViewQueryLimit

УсловиеРезультат
is_admin = 1"" — без ограничений
queries.is_public = 1"" — ограничения сущности не применяются

грантов нет and 1 = 0 — пустой список без ошибки

4. Использование в Lua

local errText, errNum = CheckGrantOfEntity(request.user_id, "map_orgs", "is_detail_view", id)
if errNum ~= 0 then
  output.error_code = 403
  output.error_text = "Нет доступа"
  return
end

local errText, errNum = CheckFullGrantOfEntity(sys.user_id, "map_orgs", "is_update", id)
  • Порядок результатов — текст, код; errNum ~= 0 — отказ. Примеры на стенде: REST auditinfo, its_req_reassign.
  • Роли REST, only_auth и bp_process_roles решают, кто может вызвать сервис или процесс, но не проверяют строки. REST, работающий с записью по id из запроса, проверяет грант сам.
  • SqlQueryRows/SqlExec2 ограничения не применяют.
  • Пропускает ли Lua-обёртка администратора — на стенде не проверено.

5. Как выдать доступ

Список и карточка по автоограничению «все строки»

insert into entity_grants (role_id, entity_id, view_limit_id, is_list_view, is_detail_view, is_insert, is_update, is_delete, title)
select r.id, e.id, v.id, 1, 1, 0, 0, 0, e.code
from roles r, entities e
join entity_view_limits v on v.entity_id = e.id and v.is_auto = 1
where r.code = 'map_manager' and e.code = 'map_orgs'
  and not exists (select 1 from entity_grants g
                  where g.role_id = r.id and g.entity_id = e.id and g.view_limit_id = v.id);

Своё ограничение «мои записи»

insert into entity_view_limits (entity_id, code, title, subquery, is_auto)
select id, 'cln_orders_my', 'Мои заказы', 'main.created_by = :user_id', 0
from entities where code = 'cln_orders';

Служебные БП (модуль core)

  • role_grant_all_view_access_mod — даёт роли список и карточку на все справочники её модуля.
  • entity_view_limits_upsert — проверяет SQL ограничения, ошибку пишет в warning_text.
  • roles_copy_grants — несмотря на название, копирует только пункты меню (role_menus), не гранты.

6. Частые ошибки

  • Сущность, страницы и меню созданы, а грантов нет — у admin всё работает, у остальных пустые списки и «Access Denied». Проверять под обычным пользователем.
  • Грант без view_limit_id не работает. У 45 сущностей стенда нет автоограничения — сначала создать 1 = 1.
  • В subquery обращаться к колонкам через main..
  • Ограничения ролей объединяются через OR — сузить доступ другой ролью нельзя.
  • is_list_view и is_detail_view — разные флаги: нужны оба.
  • queries.is_public = 1 снимает ограничения сущности в списке.
  • readonly_mode действует только на запись.
